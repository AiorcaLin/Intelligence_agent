# 资源评估 — 云服务器建议（第 2 轮 · 结论）

**日期**：2026-04-12  
**输入假设**：开发验证阶段；仅本人使用；模型为 **DeepSeek** + **OpenRouter（Claude）**；暂不做视频；人在成都、需稳定访问境外 API；目标为**选型云服务器并把项目跑起来**。

---

## 1. 运行本仓库时，机器上实际会跑什么

| 层级 | 组件 | 资源特点 |
|:---|:---|:---|
| 容器（`docker-compose.yml`） | PostgreSQL 16、Redis 7、Chroma | 常驻进程；磁盘随数据增长 |
| 本机进程 | FastAPI（Uvicorn）、Celery Worker + Beat | Python 进程；Beat 有定时任务 |
| 本机进程 | Next.js（`dev` 或 `build`+`start`） | **构建**时内存峰值往往高于运行期（见下文引用） |
| 不外购 GPU | LLM 走云端 API | 云主机以 **CPU + 内存 + 磁盘 + 出站 HTTPS** 为主 |

**说明**：LLM 不本地推理时，**GPU 不是刚需**；瓶颈更常见于 **内存（尤其 Next 构建 + 多容器）** 与 **访问境外 API 的出站网络质量**。

---

## 2. 出站网络依赖（与「成都访问国外网站」直接相关）

云服务器要能稳定访问下列 **HTTPS（443）** 端点（用于鉴权与调用；具体以你 `.env` 配置为准）：

| 依赖 | 典型域名 / 说明 | 参考 |
|:---|:---|:---|
| DeepSeek | `https://api.deepseek.com`（及兼容的 `/v1` 路径） | [DeepSeek API — Your First API Call](https://api-docs.deepseek.com/) 中表格给出 `base_url` 为 `https://api.deepseek.com`。**解释**：这是官方文档对服务端出站目标的最小定义，防火墙/安全组需放行到该主机。 |
| OpenRouter（Claude） | `https://openrouter.ai`（常见 OpenAI 兼容路径为 `/api/v1`） | [OpenRouter Quickstart](https://openrouter.ai/docs/quickstart)。**解释**：路由与鉴权以官方文档为准，评估「能否连上」时应从该站点的 API 基址做连通性测试。 |
| 嵌入向量（当前代码默认） | OpenAI Embeddings：`api.openai.com` 等 | 仓库中 `backend/utils/embedding.py` 使用 `text-embedding-3-small`。**解释**：若不改嵌入实现，主机需能访问 OpenAI API；若仅国内机房且国际出口差，这里容易成为「能登录但不能索引/检索」的断点。 |

**实践建议（不涉及具体翻墙工具）**：选好云厂商与地域后，在实例上对上述域名做 `curl`/HTTPS 探活；若失败，优先换 **国际出口更稳定的地域/线路** 或该云厂商的 **国际带宽/精品网** 产品，而不是先加机器规格。

---

## 3. 地域与线路（面向你的约束）

- **国际 API 为主**（OpenRouter、默认 OpenAI 嵌入）：常见做法是选 **香港 / 新加坡 / 东京** 等境外或强国际出口区域，降低跨境抖动与超时。  
- **国内机房**：并非不可行，但需确认套餐是否包含 **稳定的出境 HTTPS**；成都到海外机房的延迟对个人开发通常可接受，**稳定性比绝对延迟更重要**。  
- **DeepSeek**：服务端在中国大陆访问 `api.deepseek.com` 一般相对友好，但仍应以你实际 VPS 上的探活为准。

---

## 4. 云服务器规格建议（单人、先跑通）

以下为 **单机同时跑**：Docker（PG+Redis+Chroma）+ 后端 + Celery + Next 的粗算区间；数字为工程上常用保守区间，非 SLA。

| 档位 | vCPU | 内存 | 系统盘 | 适用说明 |
|:---|:---:|:---:|:---:|:---|
| **最低尝试** | 2 | **4 GB** | ≥ **40 GB** SSD | 可能偏紧：`next build` 与多个容器叠加时易触顶；可按 [Next.js Memory Usage](https://nextjs.org/docs/app/guides/memory-usage) 思路在构建时限制堆或拆分构建步骤。**解释**：官方文档强调构建/运行时的内存行为差异，低配机应先保证「构建不 OOM」再谈并发。 |
| **推荐（省心）** | 2–4 | **8 GB** | **60–80 GB** SSD | 单人开发验证最省心；留有余量给 Docker 层、Chroma 与日志。 |
| **磁盘** | — | — | 视数据 | PostgreSQL 与 Chroma 持久化增长；不跑视频仍建议 **≥40GB** 起步以免很快满盘。 |

**PostgreSQL**：内存调优与 `shared_buffers` / `work_mem` 等关系见 [PostgreSQL — Resource Consumption](https://www.postgresql.org/docs/current/runtime-config-resource.html)。单人轻载下默认容器配置通常可起步；数据变大后再按文档调参。**解释**：官方从参数关系说明「内存不是单一数字」，与上文表中的 **8GB 整机** 搭配时，轻载 Postgres 一般不是首瓶颈。

---

## 5. 与本仓库相关的实现提示（避免「机器够但仍跑不起来」）

1. **OpenRouter + Claude**：当前 `backend/utils/llm_router.py` 中 `anthropic/...` 分支使用 `CLAUDE_API_KEY` 直连 Anthropic 风格调用；若你统一走 **OpenRouter**，需在配置与 LiteLLM 的 `model` / `api_base` 上与 OpenRouter 文档对齐（例如使用 OpenRouter 提供的 API 基址与密钥），否则会出现「密钥对了但仍请求错端点」的问题。  
2. **嵌入**：默认走 OpenAI Embeddings；若你不想依赖 `api.openai.com`，需后续改为兼容 OpenRouter 或其它国内可达的嵌入服务（属功能改造，超出纯资源评估）。

---

## 6. 结论清单（可直接用于选型）

- **目标**：仅验证跑通 + 单人使用 → **2 vCPU / 8 GB RAM / 60GB+ SSD** 是较稳妥的起点；**4 GB** 可试但要有应对构建 OOM 的心理准备。  
- **GPU**：非必需（云端 LLM）。  
- **网络**：优先验证 **`openrouter.ai`、`api.deepseek.com`、以及嵌入所用 OpenAI 端点** 的 HTTPS 出站；这是你当前地理与业务约束下的关键风险点。  
- **地域**：优先考虑国际出口稳定的区域或线路；具体以各云厂商实测为准。
