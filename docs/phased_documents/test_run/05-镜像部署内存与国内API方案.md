# 镜像部署、内存与「国内可用 API」方案（第 5 轮 · 阶段性总结）

**日期**：2026-04-12  
**背景**：考虑把 **Docker 镜像构建后上传云端** 再部署；关心是否因此 **不再需要高内存**；无法为 **Claude / OpenAI 官方** 充值；本机 **16 GB RAM**、空闲前已占用约 **71%**；暂无云厂商与预算上限，单人使用。

---

## 1. 「镜像上云」之后，还需要高内存吗？

**结论要拆成两件事：构建 vs 运行。**

| 阶段 | 内存主要花在哪 | 镜像上云能否省内存 |
|:---|:---|:---|
| **构建**（`docker build`、`next build`、装依赖） | 编译与打包峰值往往很高 | **能省本机内存**：在 **CI 或云端构建机** 上完成构建，笔记本不必扛 `next build` 峰值。**解释**：你减轻的是「造镜像的那台机器」的负担，与镜像是否上传无必然关系，关键是 **构建发生在哪里**。 |
| **运行**（容器里的 Postgres / Redis / Chroma / 后端 / Celery / 前端） | 进程常驻与数据缓存 | **不能省云服务器内存**：部署目标机仍要为这些进程分配 RAM；镜像只是打包好的文件系统，**不降低运行时 RSS**。**解释**：Docker 将应用与依赖打包为镜像（见 [Docker 文档 Get started / 镜像与容器概念](https://docs.docker.com/get-started/)），运行时仍需为容器内进程分配资源。 |

因此：

- **对笔记本**：若你 **永远不在本机构建** 全栈镜像、只在云上构建/拉镜像，**本机内存压力会小很多**（你当前 71% 占用主要来自系统与其它软件，未必留给 Docker）。
- **对云主机**：单人跑通仍常见落在 **约 4–8 GB** 量级（与先前 `02` 篇一致），**不是「很低内存就够」**，只是通常不需要 32 GB 那种规格。

**一句话**：镜像化解决的是 **交付与重复构建**；**运行内存** 仍由 **实际跑的服务** 决定。

## 2. 关于 API：在「国内能付费」约束下的更好方案

当前仓库特点简述：

- **对话/分析**：`backend/utils/llm_router.py` 已通过 **LiteLLM** 调模型；**DeepSeek** 已按 `DEEPSEEK_API_KEY` + `DEEPSEEK_BASE_URL` 走国内可达的 `https://api.deepseek.com`（见 [DeepSeek API 文档](https://api-docs.deepseek.com/)）。
- **向量嵌入**：`backend/utils/embedding.py` 默认使用 **OpenAI** 官方客户端与 `text-embedding-3-small`，依赖 `OPENAI_API_KEY` —— 这正是你**不想绑定 OpenAI 充值**时的首要改造点。

### 2.1 推荐策略（工程上清晰、成本可控）

1. **主 LLM**：继续以 **DeepSeek** 为主（国内充值与线路相对友好），在 LiteLLM 里保持 `deepseek/...` 模型名与现有路由一致。  
2. **替代「Claude 做分析/摘要」**：不必死磕 Anthropic 官方或 OpenRouter（若你无法为其充值），可二选一：  
   - **同一 DeepSeek 模型** 承担更多任务类型（最简单，少密钥）；  
   - 或接入 **阿里云通义（DashScope）/ 智谱 / 月之暗面 等** 国内可开票、可人民币充值的 API，通过 LiteLLM 统一模型名切换。**解释**：LiteLLM 以「提供商/模型」形式聚合多厂商，减少每家装一套 SDK 的成本。**参考**：[LiteLLM Providers](https://docs.litellm.ai/docs/providers)。  
3. **嵌入（Embedding）**：把 `embedding.py` 从「写死 OpenAI 官方端点」改为 **OpenAI 兼容接口**（`base_url` + `api_key`），指向例如：  
   - **DashScope** 兼容模式的 embeddings；  
   - 或 **硅基流动（SiliconFlow）** 等提供 OpenAI 兼容 `/v1/embeddings` 的服务。  
   改完后需 **固定维度**（`EMBEDDING_DIMENSIONS`）与 Chroma 中已有向量一致，或 **重建向量库**（换维度时旧数据不能混用）。  
4. **统一网关（可选）**：自建或托管 **LiteLLM Proxy**，在网关层配好各厂商 Key 与路由，业务侧只打一条网关 —— 便于以后换厂商而不改业务代码。**参考**：同上 LiteLLM 文档体系。

### 2.2 OpenRouter 的定位

- 适合「一个 Key 多模型、国际卡可用」的场景；你当前 **充值受限** 时，它不应作为唯一依赖。  
- 若未来能使用其支持的支付方式，再作为 **Claude 等模型的聚合入口** 即可。

## 3. 本机 16 GB、已用 71%：说明什么？可怎么做？

- **约 71% × 15.7 GB ≈ 11.1 GB 已用**，剩余约 **4.5 GB** 量级。再开 **Docker Desktop（WSL2）+ 多容器 + IDE + 浏览器**，很容易触顶或严重换页，体感「卡」。  
- **与「能不能开发」**：你**不必**在本地跑全栈；可选路径包括：  
  - **仅连云端已部署 API**，本机只跑前端 `npm run dev` 或甚至纯远程调试；  
  - 或 **缩小本地栈**（例如 DB/Redis 全在云上，本机只跑后端进程）；  
  - 关闭占用内存的大进程（浏览器标签、其它虚拟机），并为 **WSL2 / Docker Desktop** 设合理内存上限（在 `.wslconfig` 等处，属系统调优，按微软/WSL 文档操作）。

## 4. 云花费预期（单人、无厂商偏好）

- **小规格 VPS**（2 vCPU、4–8 GB、小带宽）月费通常落在 **几十到一两百元人民币** 量级（随厂商与活动波动，此处不给具体数字以免过时）。  
- **API**：DeepSeek 等按量计费，单人低频使用往往 **低于机器费用**；以各平台实时价目为准。  
- **结论**：优先把 **「能稳定访问你选的国内/兼容 API」** 作为选区与线路条件，再比价格。
